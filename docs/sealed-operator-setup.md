# Sealed local operator setup transport candidate

This is a bounded implementation toward automated azd setup, **not completed azd
wire-up**. Local cryptographic tests and private VM/Django acceptance are recorded
below; the complete Azure setup handoff and browser delivery remain unverified.
It adds no Azure service or tenant grant. The existing
private plaintext qualification artifact remains supported when no recipient is
supplied; there is no automatic fallback from sealed mode to that artifact.

## Contract

The PowerShell 7.6 module `experiments/server/SealedSetup.psm1` creates a fresh
in-memory RSA-3072 recipient. Its private key is never serialized or sent to the
server. The public key is canonical base64 DER SubjectPublicKeyInfo, exponent
65537. `Get-SantaSetupTargetDigest` hashes length-prefixed UTF-8 exact username
and email, matching the server without Unicode normalization ambiguity.

The existing `operator_access` command optionally takes `--recipient-public-key`,
`--context-sha256`, and `--sealed-stdout`. Context is an opaque lowercase SHA-256
digest generated by the caller from its verified deployment/request selection.
Key/algorithm, context, selected target and configured HTTPS origin are validated,
and maximum-size encryption is tried, **before** any user security mutation or
output reservation. Actual encryption occurs inside the user transaction; an
encryption/size failure can still roll back. Exclusive artifact writing remains
after commit, with the existing truthful partial-failure handling.

Only setup URL, expiry and target primary key are encrypted. Verbose reasons,
Unicode identities and role metadata are not transported. Each envelope uses a
new AES-256 key and 96-bit nonce, AES-GCM with a 128-bit tag, and RSA-OAEP with
SHA-256/MGF1-SHA-256 for wrapping. AAD binds protocol version/algorithm, operation,
recipient fingerprint, caller context and exact-target digest. It is bounded to
2600 ASCII JSON bytes so the final `SANTA_SEALED_SETUP_JSON:` output line leaves
room within Azure Run Command's roughly 4 KiB output tail. Truncation or a missing
marker must fail closed; it must never trigger a blind security-operation retry.

`Receive-SantaSetupEnvelope` requires the independently retained context, mode,
target digest and expected HTTPS origin. It rejects algorithm/schema/duplicate
field/binding/tag/expiry/path/target-ID errors. It either requests normal local
browser navigation with explicit `-OpenBrowser`, or writes an explicitly selected
absent local artifact with owner-only Windows ACL / Unix 0600 permissions. It
rejects Windows streams, UNC/device namespaces and nonlocal drive types before
creation, and requires existing non-link parent directories. The selected local
Windows filesystem must be NTFS or ReFS. Before writing plaintext, the newly
created handle must report the expected owner and a protected owner-only full
control DACL; Unix handles must report exactly 0600. A failed check retains an
empty artifact and returns failure, never plaintext fallback. The selected local
directory must be trusted against concurrent replacement; this is not a filesystem
sandbox or protection from a malicious administrator. It returns only a nonsecret
delivery receipt. A browser-open request is not proof
that a browser opened or that setup/MFA completed. Private key disposal and byte
buffer clearing are best-effort memory cleanup, not a forensic erasure guarantee.
The future wrapper must also dispose the recipient in its own `finally` block,
including when PowerShell rejects arguments before entering the receive function.

Encryption protects recipient confidentiality and ciphertext integrity; **it does
not authenticate the sender**. Anyone with the public key can create an envelope.
Authentic delivery must come from the explicitly selected, authorized Azure/host
operation. AAD is not a substitute for verifying that authority.

## Remaining azd/Run Command integration

Do not expose this as a finished deployment flow until the shared wrapper:

1. Verifies exact tenant/subscription, tagged RG/VM, deployed image, current
   Compose/project hashes and selected HTTPS origin through the existing normal
   cached/broker/browser Azure CLI session. No automatic grants or device code.
2. Creates the ephemeral recipient locally and a fresh nonce, and hashes an
   unambiguous request record containing those verified bindings, operation and
   exact target digest. Never accept a deployment binding supplied by the result.
3. Sends only the public key and structured UTF-8/base64 arguments through Run
   Command. Invoke the installed command; never interpolate user data into shell
   syntax or send private keys/passwords. Do not stream the remote artifact.
4. Captures the result privately, accepts exactly one complete bounded ciphertext
   marker only after terminal command success, and decrypts/delivers locally.
   Neither plaintext URI nor private artifact may enter Azure output, chat,
   transcript, CI artifacts or issue comments.
5. Handles timeout/partial commit using existing action inspection and an explicit
   encrypted-artifact readback/checkpoint. Do not replay bootstrap/recovery on an
   unknown outcome. If the recipient key is lost, an owner must deliberately
   reissue recovery after inspecting state; decryption is not recoverable.

Public hostname/TLS admission, real browser acceptance, remote authority binding
and end-to-end Azure transport are separate unverified gates. Tests exercise real
local Python/.NET crypto, tamper rejection, Unicode digest interoperability,
private file creation and collision handling; they do not simulate those gates.
The private Django harness additionally tests pre-mutation key rejection and
transaction rollback on encryption failure. Its actual runtime acceptance follows.

## Actual private Django acceptance, 2026-11-06

A fresh isolated Santa-profile stack passed all **13 recovery request cases**,
including invalid-recipient rejection without account/output changes, real
recipient encryption/decryption, encryption-failure rollback, and truthful
post-commit artifact-write failure without a success marker or plaintext fallback.
The same image passed all 15 MFA cases, Redis interruption checks, full synthetic
Monitor device HTTP sync, 89 bounded HTTP checks and indexing of two Santa events.
Audit posting was mocked in the isolated recovery database; delivery is unproven.

The first image build failed because the combined installer exceeded Docker's
65,535-byte physical-line limit. The generator now compresses that installer for
transport and restores identical bytes before its existing module hash checks
and execution. The successful new build used a separate Dockerfile and unit;
the failed build, prior stacks and their data were retained.

The integrated template and all **158 Pester tests** passed on PowerShell 7.6.9
and Pester 6.2.0. Local Python/.NET crypto vectors used the existing isolated
Azure CLI Python with cryptography 48.0.1; hosted Windows/Linux checks also passed.
These results do not prove the complete Azure ciphertext handoff, authentic
remote deployment binding, browser/TLS setup, audit indexing, backup authority,
host power-loss recovery or native Mac sync. See the separate
[transport slice](setup-transport-slice.md) for its remaining integration gates.
